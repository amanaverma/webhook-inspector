# Architecture

Eight diagrams, in the order they build on each other: the system map first,
then the two paths a request can take through it, then the state machine that
keeps delivery safe, then the shape of what gets stored.

The two overview diagrams are checked-in SVGs with a light and a dark variant,
generated by `docs/diagrams/render.py`. Edit that script and re-run it rather
than editing the SVGs by hand. The remaining diagrams are mermaid and render
inline on GitHub.

The load-bearing rule is that steps 1 to 4 finish without waiting on step 6. A
slow or unreachable forward target must never slow down capture, so the worker
reads its work from the database rather than from the request that created it.

## 2. Capture path

What happens between a provider sending a request and it appearing on screen.

sequenceDiagram
    autonumber
    participant P as Provider
    participant A as API
    participant R as Redis
    participant D as PostgreSQL
    participant B as Browser

    P->>A: ANY /i/:slug/* with body
    A->>R: consume rate limit token
    alt bucket empty
        A-->>P: 429 Too Many Requests
    else allowed

The 200 is sent before any delivery work exists. Everything after it is the
service's problem, not the provider's.

## 3. Delivery path

Delivery is a separate loop with its own failure handling.

```mermaid
%%{init: {'theme':'base','themeVariables':{'fontFamily':'ui-sans-serif, system-ui, sans-serif','fontSize':'15px','primaryColor':'#0f766e','primaryTextColor':'#ffffff','primaryBorderColor':'#0b5551','secondaryColor':'#4338ca','secondaryTextColor':'#ffffff','secondaryBorderColor':'#312e9e','tertiaryColor':'#1e293b','tertiaryTextColor':'#e2e8f0','tertiaryBorderColor':'#475569','lineColor':'#64748b','textColor':'#7d8996','actorBkg':'#0f766e','actorTextColor':'#ffffff','actorBorder':'#0b5551','actorLineColor':'#94a3b8','signalColor':'#64748b','signalTextColor':'#7d8996','sequenceNumberColor':'#ffffff','noteBkgColor':'#1e293b','noteTextColor':'#e2e8f0','noteBorderColor':'#475569','labelBoxBkgColor':'#0f766e','labelBoxBorderColor':'#0b5551','labelTextColor':'#ffffff','altSectionBkgColor':'transparent','attributeBackgroundColorOdd':'transparent','attributeBackgroundColorEven':'transparent'}}}%%
sequenceDiagram
    autonumber
    participant W as Delivery worker
    participant D as PostgreSQL
    participant T as Forward target

    loop every tick
        W->>D: claim pending deliveries (SKIP LOCKED)
        D-->>W: rows due for attempt
        W->>D: insert attempt row with dedupe_key
        Note over W,D: unique(dedupe_key) makes a<br/>crash-restart replay a no-op
        W->>T: replay stored method, headers, raw body
        alt 2xx
            T-->>W: success
            W->>D: state = sent
        else 4xx
            T-->>W: client error
            W->>D: state = dead (no retry)
        else 5xx, timeout, DNS failure
            T-->>W: failure
            W->>D: state = failed, schedule backoff
        end
    end
```

A 4xx is the target saying the payload is wrong. Retrying it only wastes
attempts, so it is terminal. A 5xx or a timeout is the target saying "not
now", which is worth retrying.

## 4. Delivery state machine

```mermaid
%%{init: {'theme':'base','themeVariables':{'fontFamily':'ui-sans-serif, system-ui, sans-serif','fontSize':'15px','primaryColor':'#0f766e','primaryTextColor':'#ffffff','primaryBorderColor':'#0b5551','secondaryColor':'#4338ca','secondaryTextColor':'#ffffff','secondaryBorderColor':'#312e9e','tertiaryColor':'#1e293b','tertiaryTextColor':'#e2e8f0','tertiaryBorderColor':'#475569','lineColor':'#64748b','textColor':'#7d8996','actorBkg':'#0f766e','actorTextColor':'#ffffff','actorBorder':'#0b5551','actorLineColor':'#94a3b8','signalColor':'#64748b','signalTextColor':'#7d8996','sequenceNumberColor':'#ffffff','noteBkgColor':'#1e293b','noteTextColor':'#e2e8f0','noteBorderColor':'#475569','labelBoxBkgColor':'#0f766e','labelBoxBorderColor':'#0b5551','labelTextColor':'#ffffff','altSectionBkgColor':'transparent','attributeBackgroundColorOdd':'transparent','attributeBackgroundColorEven':'transparent'}}}%%
stateDiagram-v2
    [*] --> pending: request captured on a bin with a forward URL
    pending --> sent: target answered 2xx
    pending --> dead: target answered 4xx
    pending --> failed: timeout, DNS failure, or 5xx
    failed --> pending: backoff elapsed and attempts < 5
    failed --> dead: attempt 5 exhausted
    sent --> [*]
    dead --> pending: manual replay
    sent --> pending: manual replay
```

Backoff is exponential with jitter: roughly 1s, 4s, 15s, 60s, 300s, each
shifted by a random fraction so a batch of failures does not retry in lockstep.

`requests` is indexed on `(bin_id, received_at DESC, id DESC)`, which is the
exact order the list endpoint pages through, so the query is an index scan
rather than a sort.

## 6. Live tail

Two clients on the same bin, and one of them reconnecting.

```mermaid
%%{init: {'theme':'base','themeVariables':{'fontFamily':'ui-sans-serif, system-ui, sans-serif','fontSize':'15px','primaryColor':'#0f766e','primaryTextColor':'#ffffff','primaryBorderColor':'#0b5551','secondaryColor':'#4338ca','secondaryTextColor':'#ffffff','secondaryBorderColor':'#312e9e','tertiaryColor':'#1e293b','tertiaryTextColor':'#e2e8f0','tertiaryBorderColor':'#475569','lineColor':'#64748b','textColor':'#7d8996','actorBkg':'#0f766e','actorTextColor':'#ffffff','actorBorder':'#0b5551','actorLineColor':'#94a3b8','signalColor':'#64748b','signalTextColor':'#7d8996','sequenceNumberColor':'#ffffff','noteBkgColor':'#1e293b','noteTextColor':'#e2e8f0','noteBorderColor':'#475569','labelBoxBkgColor':'#0f766e','labelBoxBorderColor':'#0b5551','labelTextColor':'#ffffff','altSectionBkgColor':'transparent','attributeBackgroundColorOdd':'transparent','attributeBackgroundColorEven':'transparent'}}}%%
sequenceDiagram
    autonumber
    participant B1 as Browser A
    participant B2 as Browser B
    participant A as API
    participant D as PostgreSQL

    B1->>A: GET /api/bins/:slug/stream
    B2->>A: GET /api/bins/:slug/stream
    A->>D: LISTEN new_request

    D-->>A: NOTIFY id=42
    A-->>B1: event id=42
    A-->>B2: event id=42

    loop every 15s
        A-->>B1: heartbeat comment
        A-->>B2: heartbeat comment
    end

    Note over B2,A: network drops
    B2->>A: reconnect, Last-Event-ID = 42
    A->>D: SELECT rows after id 42
    A-->>B2: backfill, then live again
```

Two details carry this: the heartbeat keeps proxies from closing an idle
stream, and `Last-Event-ID` lets a reconnecting client backfill instead of
silently missing whatever arrived while it was gone.

The API process and the delivery worker run in the same deployment but as
separate process types, so the worker can be scaled or restarted without
interrupting capture.
